# AI-секретарь: готовые задания для Codex

**Основание:** ТЗ редакции 1.3, первый продуктовый этап.  
**Цель:** получить полноценное приложение, а не интерфейс с фиктивными ответами.  
**Порядок:** 1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 1.6.

## Как пользоваться

1. Поместите ТЗ редакции 1.3 в корень репозитория под именем `SPEC.md`. Этот файл сохраните рядом как `CODEX_TASKS_STAGE1.md`.
2. Отправьте Codex целиком блок задания 1.1. Затем отправляйте по одному следующему блоку после проверки отчёта предыдущего.
3. В новом сеансе открывайте тот же репозиторий. Каждый блок требует прочитать файлы контекста, поэтому переносить всю историю чата не нужно.
4. Ключи ASR/AI задавайте только через защищённые настройки среды или локальный файл среды, исключённый из Git. Не вставляйте секреты в задания или чат.
5. В конце каждой итерации проверяйте фактические результаты команд и нерешённые проблемы. Блокер одного внешнего сервиса не запрещает независимую разработку, но непроверенный сценарий нельзя считать принятым.
6. Второй продуктовый этап не запускать этими заданиями. Видео, диаризация, потоковый голос, мобильный клиент, командные роли, интеграции и большой пилот остаются в ТЗ для следующего этапа.

Промпты ниже не заменяют ТЗ: `SPEC.md` определяет продукт, конкретный промпт ограничивает одну итерацию. Рекомендуемый стек применяется к новому проекту; существующий рабочий стек не менять без обоснования.

## Задание 1.1. Каркас, БД и актуальный контекст

Скопируйте весь блок:

```text
Работай в текущем репозитории. Реализуй только итерацию 1.1 первого продуктового этапа AI-секретаря по SPEC.md.

Сначала:
- Прочитай SPEC.md, имеющиеся AGENTS.md, README.md, docs/PROJECT_STATE.md и относящийся к задаче код.
- Проверь git status и существующие зависимости. Не стирай чужие/несвязанные изменения и не пересоздавай работающий проект.
- Если SPEC.md отсутствует, остановись и укажи, какой документ нужен; не придумывай требования.
- Дай краткий план и затем выполни работу, не ограничиваясь планированием.

Границы:
- Не реализуй второй продуктовый этап.
- Не создавай действующие фиктивные AI-ответы, пользователей с общим паролем или секреты в коде.
- Не публикуй проект, не делай push, не изменяй производственную БД.

Сделай:
1. Для нового проекта используй TypeScript, React + Vite, Node.js + Express, PostgreSQL + Prisma, Zod, Vitest и Playwright. При существующем стеке сохрани его и запиши решение.
2. Подготовь frontend, backend и основу отдельного фонового worker. Health-проверка должна различать живой процесс и доступность необходимой инфраструктуры. Пока ASR/AI не реализованы, не выдавай их за настроенные.
3. Создай минимальную схему и миграции для первого этапа: User, Session, Meeting, Material, ProcessingRun/сохраняемое фоновое задание, кандидаты результатов, Decision, Assignment и история изменений. Сущности командных ролей, интеграций и аналитики не добавляй.
4. Зафиксируй внешний ключ/владельца встречи, состояния обработки, отдельный статус проверки кандидата и статусы исполнения new/in_progress/done/cancelled. Не смешивай статус фоновой задачи со статусом поручения.
5. Подготовь локальное подключение к PostgreSQL и постоянное защищённое хранилище аудио. Если используешь Docker, это средство локального запуска, а не обещание способа production-размещения.
6. Создай README.md, AGENTS.md, docs/PROJECT_STATE.md, docs/AI_CONTRACT.md, CHANGELOG.md и .env.example без реальных секретов. Добавь игнорирование файлов среды, аудиозаписей, паролей, временных и локальных данных.
7. В AGENTS.md запиши границы первого этапа, обязанность читать актуальное состояние, проверять регрессии, сохранять пользовательские правки и применять миграции без сброса БД.
8. Настрой реальные команды проверки типов, lint, сборки и тестов. Зафиксируй lock-файл. Для чистой установки подготовь инструкцию зависимостей и миграций.

Проверь:
- Frontend и backend собираются.
- Health-проверка работает.
- Миграции применяются на отдельной пустой локальной БД.
- Есть хотя бы один настоящий тест базового backend-поведения; пустой test-скрипт не считается проверкой.
- Работают команды проверки типов/lint. Если зависимости или среда недоступны, покажи конкретный блокер, не объявляй проверки успешными.

Заверши отчётом: что сделано, изменённые файлы, команды с фактическими результатами, ограничения, следующий шаг 1.2. Обнови docs/PROJECT_STATE.md и CHANGELOG.md. Не начинай 1.2 автоматически.
```

**Готовность:** воспроизводимый запуск каркаса, схема БД, миграции, рабочие базовые проверки и документы. Это ещё не готовое приложение.

## Задание 1.2. Логин, пароль и сохранённые встречи

```text
Работай в текущем репозитории. Реализуй только итерацию 1.2 первого этапа AI-секретаря.

Сначала прочитай SPEC.md, AGENTS.md, README.md, docs/PROJECT_STATE.md, docs/AI_CONTRACT.md, проверь git status и результаты 1.1. Если предпосылка не выполнена, исправь только необходимый блокер. Дай краткий план и выполни его.

Сделай:
1. Реализуй серверный вход по уникальному логину и паролю и выход. OAuth/SSO не заменяют этот вход. Публичная регистрация, восстановление пароля и корпоративные роли не входят в задачу.
2. Предоставь документированную серверную CLI-команду создания пользователей с вводом пароля без его отображения. Не создавай встроенный общий пароль и не коммить реквизиты.
3. Храни безопасный хеш пароля, предпочтительно Argon2id. Правило пароля и параметры сессии возьми из SPEC.md.
4. Реализуй серверную сессию, обновление идентификатора после входа, cookie HttpOnly/SameSite и Secure для HTTPS, аннулирование после выхода, защиту изменяющих запросов от CSRF и ограничение попыток входа.
5. Создай интерфейс входа, защищённую навигацию, действие выхода.
6. Реализуй создание встречи с названием, датой/временем и IANA-часовым поясом. Дата загрузки не подменяет дату встречи. На этом шаге сохраняй метаданные и текстовый материал без выдуманного AI-результата.
7. Реализуй список встреч с пагинацией/поиском по названию и страницу встречи. Пока обработка ещё не подключена, честно показывай доступные функции и состояние.
8. Проверяй владельца встречи и связанных сущностей на backend. ID из URL не является разрешением доступа.

Проверь на двух отдельно созданных тестовых пользователях:
- Корректный/некорректный вход, защищённый запрос без сессии, выход и повторное использование старой сессии.
- Отказ изменяющего запроса без допустимой CSRF-защиты.
- Пользователь B не видит и не изменяет встречу/материал пользователя A даже по известному ID через прямой API.
- Данные сохраняются после перезапуска backend и повторного входа.
- Пароль и его хеш не возвращаются клиенту и не выводятся в логи.
- Есть API-тесты и E2E-сценарий вход → создание встречи → список → страница встречи → выход.

Не запускай второй этап. Не выполняй тестовые удаления в рабочей БД: используй отдельные тестовые данные/БД.

Обнови документы. В отчёте покажи результаты проверок M-01, базовой части M-06 и M-10; не объявляй готовыми AI-сценарии. Не начинай 1.3 автоматически.
```

**Готовность:** работает защищённый доступ по логину/паролю, встречи сохраняются, просмотр ограничен владельцем.

## Задание 1.3. Реальная обработка текста AI-модулем

```text
Реализуй только итерацию 1.3 первого этапа AI-секретаря в текущем репозитории.

Прочитай SPEC.md, AGENTS.md, README.md, docs/PROJECT_STATE.md и docs/AI_CONTRACT.md; проверь git status, фактические маршруты/схему и пройденные проверки 1.2. Сначала краткий план, затем реализация.

Сделай:
1. Добавь ввод текста и загрузку UTF-8 TXT по лимитам SPEC.md. Отклоняй пустой материал, неподдерживаемую кодировку и превышение лимита без потери ввода.
2. Реализуй один настоящий серверный LLM-адаптер. Выбранного провайдера/модель и ограничения проверь по актуальной документации и запиши в README. Ключ получай только из защищённой конфигурации; не проси вставить его в чат и не отправляй во frontend.
3. Используй сохраняемую задачу/ProcessingRun: backend возвращает ID, UI опрашивает статус. Перезапуск приложения не должен терять очередь и материал. Задача должна иметь тайм-аут, ограниченные повторы и защиту от параллельной повторной обработки.
4. Получай результат схемы 1.0 из SPEC.md: summary, decisions, assignments, questions, information. Проверяй его Zod/эквивалентом; схема и даты не должны зависеть только от инструкции в промпте.
5. Неизвестные исполнитель и срок — null. Относительные сроки разрешай относительно даты встречи и её часового пояса. Не угадывай человека при альтернативе и не превращай идеи, отрицания и статусные сообщения в поручения.
6. Свяжи пункт с исходной цитатой. Внутренний ID материала устанавливай на backend. Проверь источник; неподтверждённый источник блокирует подтверждение до исправления. Текст материала считается данными, не командами для системы.
7. Обработай предел контекста выбранной модели: контролируемое разбиение с объединением и сохранением источников либо явный согласованный лимит. Не обрезай текст молча.
8. Сохрани исходный материал, ProcessingRun и валидированные кандидаты результата в БД. Страница встречи показывает источник, резюме и структурированные черновики.
9. Подготовь экран проверки: раздельные решения/поручения, пустые состояния, неопределённые поля и источники. Полное редактирование/подтверждение реализуется в 1.5; пока ни один пункт не становится действующим автоматически.
10. При отсутствии настройки AI, отказе провайдера или невалидном ответе показывай честную ошибку и безопасный повтор. Демо-ответ не заменяет реальную обработку.

Проверки:
- Модульные тесты схемы, дат, источников и обработки неизвестных значений.
- API-тесты статуса, проверки владельца, неверного AI-ответа, тайм-аута, отсутствия ключа и повторного запроса.
- Регрессии входа/списка/сохранности встреч.
- E2E текст → черновик → просмотр после обновления страницы. В детерминированных тестах допустим отдельный test-only адаптер, недоступный рабочему режиму.
- Отдельно один реальный текстовый сценарий через провайдера на разрешённом/синтетическом материале. Если ключ/квота отсутствуют, зафиксируй блокер и не объявляй этот сценарий проверенным.

Не делай аудио и второй этап. Не перезаписывай ручные результаты и существующие встречи.

Обнови AI_CONTRACT.md, PROJECT_STATE.md и CHANGELOG.md. Отчёт должен разделять mock-тесты и реальные AI-вызовы, показывать статус M-02, M-04, части M-05/M-07/M-11/M-15. Не начинай 1.4 автоматически.
```

**Готовность:** текст обрабатывается настоящим AI на backend, результат валидируется и сохраняется; либо реализация готова, а конкретная внешняя проверка честно отмечена как заблокированная.

## Задание 1.4. Аудиофайлы, ASR и восстановление обработки

```text
Прочитай SPEC.md, AGENTS.md, README.md, docs/PROJECT_STATE.md, docs/AI_CONTRACT.md. Проверь состояние репозитория, схему БД, очередь и LLM-адаптер. Сохрани рабочий текстовый конвейер. Дай короткий план и выполни его.

Проверь:
- Файлы каждого заявленного формата; повреждённый файл, подмена расширения, слишком большой/длинный файл, незавершённая загрузка.
- Запрет чужого скачивания, запуска обработки и просмотра расшифровки через прямой API.
- Отсутствие ключа, тайм-аут/ошибка ASR, ошибка последующего LLM, ограничение числа повторов.
- Перезапуск worker и повтор задачи без потери состояния и дублей.

Обнови README, PROJECT_STATE, AI_CONTRACT и CHANGELOG. Отдельно укажи реализацию и фактически проверенные форматы, статус M-03 и связанных M-09/M-10/M-11/M-15. Если провайдер заблокирован, сохрани конкретный нерешённый пункт и продолжи независимую работу, не заявляя полной приёмки. Не начинай 1.5 автоматически.
```

**Готовность:** аудио использует реальное распознавание и общий AI-конвейер; ошибки и перезапуски не создают потери или дубли.

## Задание 1.5. Подтверждение, поручения, статусы и история

```text
Реализуй только итерацию 1.5 первого этапа AI-секретаря.

Прочитай SPEC.md, AGENTS.md, README.md, docs/PROJECT_STATE.md и docs/AI_CONTRACT.md. Проверь текущую схему и UI результатов. Зафиксируй краткий план и реализуй его без переписывания работающих входа, текста и аудио.

Сделай:
1. Реализуй редактирование, подтверждение и отклонение каждого черновика решения/поручения. Пустые или неверные обязательные поля проверяй и в UI, и на backend.
2. Для подтверждения поручения пользователь должен разрешить неопределённость исполнителя. Исполнитель может быть участником, не имеющим аккаунта. Не создавай ему учётную запись и не выдавай доступ автоматически.
3. Не требуй выдумывать срок: разреши подтвердить поручение без срока, сохранив null. Срок и его исходная формулировка различаются; явное время/часовой пояс не теряются.
4. Сохраняй подтверждённые Decision и Assignment в нормализованных таблицах транзакционно. Повторное нажатие/повтор API-запроса подтверждает тот же пункт, не создаёт второй.
5. Отдельно храни draft/approved/rejected кандидата и new/in_progress/done/cancelled поручения. Новый подтверждённый Assignment получает new.
6. Дай владельцу менять текст, исполнителя, срок и статус; выполнять и возвращать задачу в работу. Просрочка вычисляется для незавершённых/неотменённых задач; выполнение отмечает пользователь, а не модель.
7. Сохраняй историю изменений: автор, время и изменённые значения. Проверь права на изменяемый объект.
8. Сохрани связи с источником. Отклонённый пункт не появляется среди действующих поручений.
9. Повторный анализ создаёт новую версию черновиков, но не стирает подтверждённые записи и ручные исправления. Не переноси автоматически новые кандидаты в действующие задачи и не подтверждай одну версию повторно.
10. Заверши список и страницу встречи: резюме, решения, поручения, статусы, источники, история, поиск по тексту поручений и фильтр по статусу.
11. Проверь интерфейс при 360 px и на desktop: клавиатура, понятные подписи, загрузка/ошибка/пустой список; смысл статусов не только в цвете.

Проверки:
- Полный сценарий текст/аудио → черновик → исправление → подтверждение → изменение статуса → повторный вход/перезапуск → прежние данные.
- Подтверждение при неизвестном исполнителе, отсутствии срока, неверном источнике и некорректной дате.
- Повторное подтверждение и одновременные запросы не создают дублей.
- Новая версия анализа не удаляет/перезаписывает подтверждённый результат.
- Пользователь B не изменяет результаты A через известный ID.
- Прежние тесты входа, текстового и аудиоконвейера остаются успешными.

Используй отдельную тестовую БД. Не добавляй второй этап, внешние уведомления и автосоздание действующих поручений.

Обнови документы. В отчёте укажи статус M-05–M-10 и M-16, реальные команды/результаты и блокеры. Не начинай 1.6 автоматически.
```

**Готовность:** результаты превращаются в проверенные рабочие записи, изменения сохраняются, повторные действия не портят данные.
